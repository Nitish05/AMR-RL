# Genesis Studio relationship

AMR-RL uses **Genesis World** directly for simulation. **Genesis Studio** is
treated as an optional, version-recorded external tool for scene authoring and
inspection:

* `amr_rl.sim.studio_export.export_project(world, path)` writes a Studio project
  (schema 4) for any AMR-RL world: the generated robot URDF (non-fixed base), walls,
  obstacles and fixtures as primitives, lights, and the onboard camera as a
  link-attached sensor on `camera_link`.
* Exports for `arena`, `home_a` and `heldout_b` are in `projects/`. They were
  validated against Studio's own `genesis_studio.models.Project` (Studio commit
  `cd20c8c685f2b51263814fd0a6296bfd849bdce6`) — run
  `GENESIS_STUDIO_SRC=<Genesis-Studio>/apps/api/src pytest tests/test_studio_export.py`.
* Textured wall/floor appearance is generated by AMR-RL at simulation time and is
  not represented in the Studio export (primitives only).
* AMR-RL never imports Studio at runtime, never writes into the Studio checkout,
  and does not require it to be installed. Studio's `genesis-world[render]==1.3.2`
  pin matches the version AMR-RL was validated with.

Why not run AMR-RL *inside* Studio? Studio's native viewer is a good inspection
shell, but the AMR runtime needs its own lockstep loop (camera capture →
perception → supervisor → wheel commands) and ground-truth-free boundaries. The
capability check that mattered — robot-mounted camera (`camera.attach`), physical
wheel joints under velocity control, a screen surface — is satisfied by Genesis
World 1.3.2 itself (`tests/test_sim_genesis.py`). Opening the exported project in
Studio's native editor on macOS was not exercised in this delivery (ledger).
